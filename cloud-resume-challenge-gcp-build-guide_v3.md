# The Cloud Resume Challenge — GCP Build Guide (v3)

**Architecture**

```
Browser (loads resume site from GCS bucket behind HTTPS Load Balancer + Cloud CDN)
   │  index.html (resume) + style.css + counter.js
   ▼
POST https://REGION-PROJECT_ID.cloudfunctions.net/write-number
   │  Cloud Run function "write-number" (Python, functions-framework, 2nd gen)
   ▼
Cloud SQL for MySQL  (primary path — single-row `visitors` counter, via Unix socket)
```

The browser loads `index.html`/`counter.js` from a Cloud Storage bucket that sits behind an HTTPS Application Load Balancer with Cloud CDN enabled. The `counter.js` file calls your Cloud Run function's HTTPS endpoint once per page load (a separate origin, which is why the function needs CORS headers). The function atomically increments a visitor count in the database and returns the new total, which `counter.js` displays on the page.

## Engineering Note: Why this guide uses Cloud SQL instead of Firestore

Challenge requirement 8 suggests Firestore for the visitor counter. This build uses **Cloud SQL for MySQL** instead. The visitor counter is a single number that needs an atomic read-modify-write (`count = count + 1`) operation, which is a perfect use case for a relational database's row-level locking. Firestore is a *document* database, being a great fit when you have loosely structured, hierarchical records that don't share a rigid schema, but an unnecessary feature for one integer that never changes shape. A `visitors` table with one row is the simpler, more appropriate tool here. Firestore's own docs point to its `Increment()` sentinel specifically because naive read-then-write race conditions are a known pitfall for counters in a document store, which you can prevent with a relational `UPDATE ... SET count = count + 1` operation.

## 0. Prerequisites

- A Google Cloud Platform (GCP) account, with billing enabled (the load balancer, Cloud SQL, and domain registration all have small costs while the function, storage, and Cloud Build are free or near-free at this scale).
- Owner/Editor access on the GCP project, or equivalently: Cloud Functions Admin, Cloud SQL Admin, Datastore Admin, Storage Admin, Load Balancer Admin, IAM Admin.
- APIs enabled: **Cloud Run**, **Cloud Build**, **Artifact Registry**, **Cloud SQL Admin API**, **Compute Engine API** (for the load balancer). Enable any of these from **APIs & Services → Library** in the console if not already on.
- **Challenge requirement 1 — Certification:** the [Google Cloud Digital Leader](https://cloud.google.com/learn/certification/cloud-digital-leader) certification, listed on your resume. ExamPro (a challenge sponsor) offers free video lessons and a practice exam if you haven't sat it yet.
- Resume content ready to mark up as HTML, in a file named `index.html`. The actual writing/editing of your resume content is up to you; this guide covers the technical build once you have your content.
- Two empty GitHub repositories: one for the backend (`cloud_resume_backend`), one for the frontend (`cloud_resume_frontend`).

### Terraform Equivalent: Project Setup

Every section below also has a **Terraform equivalent** subsection, showing how to build the same resource as code instead of clicking through the console. This is how challenge requirement 12 (Infrastructure as Code) is satisfied for the database, cloud function, and everything else besides your application source code. Use one approach or the other per resource. Don't manage the same resource both ways, or `terraform apply` and your console clicks will cancel each other.

**Where things actually live:** The Terraform path is more difficult because unlike the console (which runs entirely in the browser, against GCP), Terraform splits the development work across three locations:

| Where | What lives there |
|---|---|
| **Your development PC** | The `terraform` CLI binary, your `.tf` config files (version-controlled — commit these to a repo, e.g. a new `cloud-resume-infra` repo or an `infra/` folder in an existing one), and a local `.terraform/` cache folder (provider plugin binaries — **don't** commit this one, since it is regenerated by `terraform init`). This is where the developer types every command below. |
| **A GCS bucket, in your GCP project** | Terraform's *state file* — the record of everything Terraform has created and how the pieces relate. This bucket has to exist before you ever run `terraform init`, created with a one-time `gcloud` command. Several machines (your laptop, a teammate's, CI) can all point at this same bucket and share one source of truth. |
| **The GCP project itself** (`cloud-resume-2026`) | The actual resources — the Cloud Run service, database, storage bucket, load balancer, and so on. Nothing in this table is created *on your PC*; your machine only ever sends API calls to tell GCP what to build. |

```
Your development PC                              GCP project: cloud-resume-2026
──────────────────────                           ──────────────────────────────
~/cloud-resume/terraform/        init ────────▶   gs://cloud-resume-2026-tfstate/
 ├─ providers.tf                                   cloud-resume/default.tfstate
 ├─ variables.tf                                   (the state file lives here,
 ├─ *.tf (added in later sections)                  never on your laptop)
 ├─ terraform.tfvars   (gitignored)
 └─ .terraform/         (gitignored)

 terraform plan    ── reads & compares ───────▶   live resources in the project
 terraform apply   ── creates & updates ──────▶   (Cloud Run, the database, Storage,
                                                    Load Balancer, IAM, Cloud Build…)
```

**Step 1 — on your development PC, one-time.** Install [Terraform](https://developer.hashicorp.com/terraform/install) 1.5+. (Running everything from Cloud Shell instead is a fine alternative — it has Terraform preinstalled and skips this step — but since you're working from a local folder, the rest of this walkthrough assumes your own machine.)

**Step 2 — on your development PC, one-time.** Authenticate so Terraform can talk to GCP using *your* identity:
```bash
gcloud auth application-default login
```
This opens a browser sign-in, then saves credentials to a file on your PC (`~/.config/gcloud/application_default_credentials.json` on macOS/Linux, `%APPDATA%\gcloud\application_default_credentials.json` on Windows). Every `terraform plan`/`apply` you run locally reads this file to authenticate its calls to the Google Cloud APIs — nothing more to configure for auth after this.

**Step 3 — create the state bucket, one-time.** This command can be run from your local terminal (if `gcloud` is installed there) or from Cloud Shell — either way, *where you type the command* doesn't matter, because the bucket it creates lives in GCP, not wherever you ran it from:
```bash
gcloud storage buckets create gs://cloud-resume-2026-tfstate --location=us-east4 --uniform-bucket-level-access
```
Do this **before** step 5 (`terraform init`) — the backend configuration below points at this bucket, and `init` fails if it doesn't exist yet.

**Step 4 — on your development PC.** Create a project folder and the first two config files in it, using whatever editor you like (VS Code, etc.):
```bash
mkdir -p ~/cloud-resume/terraform && cd ~/cloud-resume/terraform
```

`providers.tf`
```hcl
terraform {
  required_version = ">= 1.5"

  required_providers {
    google = {
      source  = "hashicorp/google"
      version = "~> 6.0"
    }
  }

  # Points Terraform at the remote state file living in your GCP project —
  # not at a file on this PC.
  backend "gcs" {
    bucket = "cloud-resume-2026-tfstate"
    prefix = "cloud-resume"
  }
}

provider "google" {
  project = var.project_id
  region  = var.region
}

data "google_project" "current" {
  project_id = var.project_id
}
```

`variables.tf`
```hcl
variable "project_id" {
  description = "Your GCP project ID"
  type        = string
  default     = "cloud-resume-2026"
}

variable "region" {
  description = "Region for all resources (match your Cloud SQL instance's region)"
  type        = string
  default     = "us-east4"
}
```
(Defaults are filled in from the project values at the top of this guide — override them with `-var` flags or a `terraform.tfvars` file if you ever point this at a different project.)

**Step 5 — on your development PC, in that same `terraform/` folder.**
```bash
terraform init
```
This runs entirely on your PC except for one network call: it downloads the `google` provider plugin into the local `.terraform/` folder, *and* it reaches out to the GCS bucket from step 3 to confirm it can read/write state there. Run this once per folder; you only re-run it later if you add a new provider or change the backend block.

**Step 6 — on your development PC, same folder, every time you want to preview a change.**
```bash
terraform plan
```
Terraform reads your local `.tf` files, then calls the GCP APIs to check the *current* state of the real resources in `cloud-resume-2026`, and prints a diff between the two. Read-only — nothing changes in GCP.

**Step 7 — on your development PC, same folder, when you're ready to actually build something.**
```bash
terraform apply
```
Type `yes` at the confirmation prompt. This is the one command that actually changes anything in `cloud-resume-2026` — Terraform sends the create/update API calls for each resource, GCP provisions them, and Terraform writes the updated state back to the GCS bucket (not to your PC — there's no local `terraform.tfstate` file in this setup, by design).

From here on, every "Terraform equivalent" subsection below just means: add the given resource blocks to a `.tf` file in this same `~/cloud-resume/terraform/` folder, then repeat steps 6 and 7 from that folder. You never repeat steps 1–5 — those were one-time setup.

`.gitignore` for that folder:
```
.terraform/
*.tfstate
*.tfstate.*
terraform.tfvars
```
The `.tf` files themselves *should* be committed; the state, provider cache, and any file holding real secrets should not.

## 1. Prepare the database *(Challenge requirement 8)*

### Cloud SQL (primary path)

1. If you don't already have an instance, Console → **SQL → Create instance → MySQL** → instance ID `free-trial-first-project`, set a root password, region `us-east4`. (A small `db-f1-micro` tier is plenty for a visitor counter.)
2. Console → **SQL** → click your instance → note the **Connection name** on the Overview page — `PROJECT_ID:REGION:INSTANCE_ID`, i.e. `cloud-resume-2026:us-east4:free-trial-first-project`. You'll need this exact string later.
3. Create a database: left menu → **Databases** → **Create database** → name it `visitors_db` → **Create**.
4. Create an application user: left menu → **Users** → **Add user account** → Built-in authentication → username `visitors_app`, set a strong password → **Add**.
5. Create and seed the counter table. Easiest path is **Cloud SQL Studio** (built into the console): left menu → **Cloud SQL Studio** → connect using the user/database from steps 3–4 → run:
   ```sql
   CREATE TABLE visitors (
     id INT PRIMARY KEY,
     count INT NOT NULL DEFAULT 0
   );

   INSERT INTO visitors (id, count) VALUES (1, 0);
   ```
   This table intentionally holds exactly one row — the counter increments that row in place rather than logging one row per visit, which keeps the atomic `UPDATE ... SET count = count + 1` cheap no matter how many visits you get.

(Optional but recommended) Store the DB password in **Secret Manager** instead of a plain environment variable:
- Console → **Security → Secret Manager** → **Create secret** → name `db-password`, secret value = the password from step 4 → **Create secret**.

#### Terraform equivalent: database, user, and secret


`variables.tf` (add):
```hcl

  description = "Password for the visitors_app MySQL user"
  type        = string
  sensitive   = true
}
```
Pass it at apply time rather than hardcoding it: `terraform apply -var="db_password=$(gcloud secrets versions access latest --secret=db-password)"`, or a gitignored `terraform.tfvars`.

`secrets.tf`
```hcl
resource "google_secret_manager_secret" "db_password" {
  secret_id = "db-password"
  replication {
    auto {}
  }
}

resource "google_secret_manager_secret_version" "db_password" {
  secret      = google_secret_manager_secret.db_password.id
  secret_data = var.db_password
}
```

**On the table and its seed row:** the Google Terraform provider has no resource for MySQL DDL or DML — `google_sql_database` only creates the schema, not the table or its one row. Create and seed the `visitors` table via Cloud SQL Studio as in step 5 above; this is a one-time, deliberate action outside `terraform apply`, not something it manages for you.

## 2. The Cloud Run function code

Create a local folder, e.g. `write-number-function/`, with the files below. Cloud Run functions for Python require the source file to be named exactly `main.py`.

### Cloud SQL (primary path)

**`requirements.txt`**
```
functions-framework==3.*
PyMySQL==1.1.*
```

**`main.py`**
```python
import json
import os

import functions_framework
import pymysql


_connection = None


def get_connection():
    """Lazily open (and reuse, across warm invocations) a connection to Cloud SQL."""
    global _connection
    if _connection is None or not _connection.open:
        _connection = pymysql.connect(
            # Cloud Run mounts the Cloud SQL connection at this Unix socket path
            # once the instance is attached under the function's "Connections" tab.
            unix_socket=f"/cloudsql/{os.environ['INSTANCE_CONNECTION_NAME']}",
            user=os.environ['DB_USER'],
            password=os.environ['DB_PASS'],
            database=os.environ['DB_NAME'],
            autocommit=True,
            cursorclass=pymysql.cursors.DictCursor,
        )
    return _connection


def _cors_headers():
    return {
        'Access-Control-Allow-Origin': os.environ.get('ALLOWED_ORIGIN', '*'),
        'Access-Control-Allow-Methods': 'POST, OPTIONS',
        'Access-Control-Allow-Headers': 'Content-Type',
        'Content-Type': 'application/json',
    }


@functions_framework.http
def write_number(request):
    headers = _cors_headers()

    if request.method == 'OPTIONS':
        # Preflight request
        return ('', 204, headers)

    if request.method != 'POST':
        return (json.dumps({'error': 'Only POST is supported.'}), 405, headers)

    try:
        conn = get_connection()
        with conn.cursor() as cursor:
            cursor.execute('UPDATE visitors SET count = count + 1 WHERE id = 1')
            cursor.execute('SELECT count FROM visitors WHERE id = 1')
            row = cursor.fetchone()
        return (json.dumps({'success': True, 'count': row['count']}), 200, headers)
    except Exception as err:
        print(f'DB update failed: {err}')
        return (json.dumps({'error': 'Failed to update visitor count.'}), 500, headers)
```

Both versions expose the same response shape — `{"success": true, "count": N}` — on purpose, so the frontend (`counter.js`, section 6) works unmodified no matter which database path you picked.

You can test either version locally first:
```bash
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
functions-framework --target=write_number --debug
```
(The Cloud SQL version will fail to reach `/cloudsql/...` locally unless you also run the Cloud SQL Auth Proxy; the Firestore version needs `gcloud auth application-default login` to have been run locally so the client has credentials. Local testing is optional — section 3's automated tests don't need either.)

### Terraform equivalent

No infrastructure to declare here — `main.py` and `requirements.txt` are application source, not something Terraform manages. Section 4's Terraform equivalent packages these files into a container image and deploys them.

## 3. Tests for the function

Keep test dependencies separate from runtime dependencies, so the deployed container doesn't carry test tooling it'll never use:

**`requirements-test.txt`**
```
pytest==8.*
```

### Cloud SQL (primary path)

**`test_main.py`**
```python
from unittest.mock import MagicMock

import pytest
from flask import Flask

import main

app = Flask(__name__)


@pytest.fixture
def mock_db(monkeypatch):
    """Replace get_connection() with a fake connection/cursor that returns count=43."""
    mock_cursor = MagicMock()
    mock_cursor.__enter__.return_value = mock_cursor
    mock_cursor.fetchone.return_value = {'count': 43}
    mock_conn = MagicMock()
    mock_conn.cursor.return_value = mock_cursor
    monkeypatch.setattr(main, 'get_connection', lambda: mock_conn)
    return mock_cursor


def test_options_request_returns_204(mock_db):
    with app.test_request_context('/', method='OPTIONS'):
        from flask import request
        body, status, headers = main.write_number(request)
    assert status == 204


def test_get_request_is_rejected(mock_db):
    with app.test_request_context('/', method='GET'):
        from flask import request
        body, status, headers = main.write_number(request)
    assert status == 405


def test_post_increments_and_returns_count(mock_db):
    with app.test_request_context('/', method='POST'):
        from flask import request
        body, status, headers = main.write_number(request)
    assert status == 200
    assert '"count": 43' in body
    mock_db.execute.assert_any_call('UPDATE visitors SET count = count + 1 WHERE id = 1')


def test_db_error_returns_500(monkeypatch):
    def broken_connection():
        raise RuntimeError('connection refused')
    monkeypatch.setattr(main, 'get_connection', broken_connection)
    with app.test_request_context('/', method='POST'):
        from flask import request
        body, status, headers = main.write_number(request)
    assert status == 500
```

Run either suite locally with:
```bash
pip install -r requirements.txt -r requirements-test.txt
pytest -v
```
Both test files use `flask.Flask().test_request_context()` to build a real `flask.Request` object without needing a live server — `functions_framework.http`-decorated functions accept that object directly, since functions-framework is built on Flask under the hood. Neither suite touches a real database: `mock_db` swaps out `get_connection`/`get_db` entirely, which is also why these tests run the same whether your laptop has network access to GCP or not — useful, since section 8 runs this same `pytest` command inside Cloud Build on every push.

## 4. Deploy the function from the Cloud Console

### Cloud SQL (primary path)

1. Console → search **Cloud Run** → **Functions** tab (or go directly to *Cloud Run → Functions*) → **Write a function**.
2. Configuration:
   - **Environment**: Cloud Run function (2nd gen)
   - **Function name**: `write-number`
   - **Region**: `us-east4` (same region as your Cloud SQL instance)
   - **Runtime**: Python 3.12
   - **Authentication**: "Allow unauthenticated invocations" (required so the browser can call it directly). See the security notes section about the implications.
3. Click **Next**. In the inline source editor, replace the generated `main.py` and `requirements.txt` with the Cloud SQL versions from section 2. Set **Entry point** to `write_number`.
4. Before deploying, expand **Runtime, build, connections and security settings**:
   - **Variables & Secrets** tab → add runtime environment variables:
     | Name | Value |
     |---|---|
     | `DB_USER` | `visitors_app` |
     | `DB_NAME` | `visitors_db` |
     | `INSTANCE_CONNECTION_NAME` | `cloud-resume-2026:us-east4:free-trial-first-project` |
     | `ALLOWED_ORIGIN` | `https://www.siqify.com` (use `*` temporarily until section 7 is live) |
     - For `DB_PASS`, prefer a **secret reference**: click **Reference a secret**, choose `db-password`, mount as environment variable `DB_PASS`.
   - **Connections** tab → **Cloud SQL connections** → **Add a connection** → select your existing instance.
5. Click **Deploy**. Once deployed, copy the **Trigger URL** shown at the top (e.g. `https://write-number-abcd1234-uc.a.run.app` or `https://REGION-PROJECT_ID.cloudfunctions.net/write-number`) — you'll use this in `counter.js`.

#### Terraform equivalent

Terraform's `google_cloudfunctions2_function` resource doesn't currently expose a field for attaching a Cloud SQL instance — the equivalent of the console's **Connections → Cloud SQL connections**, or `gcloud functions deploy --set-cloudsql-instances`. Since a 2nd-gen Cloud Run function *is* a Cloud Run service under the hood, the reliable way to get full Terraform coverage — Cloud SQL attachment included — is to manage it directly as a `google_cloud_run_v2_service` running the same container. It shows up in the same **Cloud Run** console page and behaves identically to what "Write a function" created.

That means you need a built container image. Section 8 covers the `Dockerfile` and the CI pipeline that builds it; push to **Artifact Registry** (Google shut down the older `gcr.io` Container Registry in March 2025):
```bash
gcloud artifacts repositories create backend-images --repository-format=docker --location=us-east4
```

`function.tf`
```hcl
resource "google_service_account" "write_number" {
  account_id   = "write-number-sa"
  display_name = "Runtime service account for write-number"
}

resource "google_cloud_run_v2_service" "write_number" {
  name     = "write-number"
  location = var.region
  ingress  = "INGRESS_TRAFFIC_ALL"

  template {
    service_account = google_service_account.write_number.email

    containers {
      image = "${var.region}-docker.pkg.dev/${var.project_id}/backend-images/write-number:latest"

      env {
        name  = "DB_USER"
        value = google_sql_user.visitors_app.name
      }
      env {
        name  = "DB_NAME"
        value = google_sql_database.visitors_db.name
      }
      env {
        name  = "INSTANCE_CONNECTION_NAME"
        value = data.google_sql_database_instance.existing.connection_name
      }
      env {
        name  = "ALLOWED_ORIGIN"
        value = "https://${var.domain}"
      }
      env {
        name = "DB_PASS"
        value_source {
          secret_key_ref {
            secret  = google_secret_manager_secret.db_password.secret_id
            version = "latest"
          }
        }
      }

      volume_mounts {
        name       = "cloudsql"
        mount_path = "/cloudsql"
      }
    }

    volumes {
      name = "cloudsql"
      cloud_sql_instance {
        instances = [data.google_sql_database_instance.existing.connection_name]
      }
    }
  }

  lifecycle {
    ignore_changes = [template[0].containers[0].image]
  }
}

# Equivalent of "Allow unauthenticated invocations"
resource "google_cloud_run_v2_service_iam_member" "public_invoker" {
  project  = var.project_id
  location = google_cloud_run_v2_service.write_number.location
  name     = google_cloud_run_v2_service.write_number.name
  role     = "roles/run.invoker"
  member   = "allUsers"
}
```
The `lifecycle { ignore_changes = [...] }` block matters once Cloud Build (section 8) is also deploying new images on every push: without it, the next `terraform apply` would silently roll the service back to whatever image tag is hardcoded above, undoing your latest deploy. Terraform manages everything about the service *except* which image is currently running — CI owns that.

```hcl
  default     = "www.siqify.com"
}
```

## 8. CI/CD for the backend: tests → build → deploy *(Challenge requirement 14)*

This is the piece that satisfies "tests get run, and only if they pass does the application get packaged and deployed" — a plain Dockerfile-type Cloud Build trigger (as used in earlier guide versions) can't run a test step first, so this section uses a full `cloudbuild.yaml` pipeline instead.

**`Dockerfile`** (repo root, alongside `main.py`, `requirements.txt`, `requirements-test.txt`, `test_main.py`):
```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

ENV PORT=8080
ENV FUNCTION_TARGET=write_number

CMD exec functions-framework --target=${FUNCTION_TARGET} --port=${PORT}
```

**`cloudbuild.yaml`** (repo root):
```yaml
steps:
  # 1. Run tests. Cloud Build stops here if pytest exits non-zero — nothing
  #    past this step runs, so a failing test blocks the deploy entirely.
  - name: 'python:3.12-slim'
    entrypoint: bash
    args:
      - -c
      - |
        pip install --no-cache-dir -r requirements.txt -r requirements-test.txt
        pytest -v

  # 2. Build the container image.
  - name: 'gcr.io/cloud-builders/docker'
    args:
      - 'build'
      - '-t'
      - '${_REGION}-docker.pkg.dev/$PROJECT_ID/backend-images/write-number:$COMMIT_SHA'
      - '.'

  # 3. Push it to Artifact Registry.
  - name: 'gcr.io/cloud-builders/docker'
    args:
      - 'push'
      - '${_REGION}-docker.pkg.dev/$PROJECT_ID/backend-images/write-number:$COMMIT_SHA'

  # 4. Deploy the new image to the existing Cloud Run resource.
  - name: 'gcr.io/cloud-builders/gcloud'
    args:
      - 'run'
      - 'deploy'
      - 'write-number'
      - '--image'
      - '${_REGION}-docker.pkg.dev/$PROJECT_ID/backend-images/write-number:$COMMIT_SHA'
      - '--region'
      - '${_REGION}'

substitutions:
  _REGION: us-east4
```

Console → **Cloud Build → Triggers → Create trigger**:
- Source: your `cloud_resume_backend` repo (connect it first if you haven't — **Connect repository** → GitHub → authorize/select the repo).
- Event: **Push to a branch**, branch regex `^main$`.
- Configuration: **Cloud Build configuration file (yaml or json)**, location `/cloudbuild.yaml`.
- **Create**.

Grant the Cloud Build service account what it needs (Console → **IAM & Admin → IAM**, find `PROJECT_NUMBER@cloudbuild.gserviceaccount.com`):
- **Artifact Registry Writer** (`roles/artifactregistry.writer`) — to push the built image.
- **Cloud Run Admin** (`roles/run.admin`) — to deploy the new revision.
- **Service Account User** (`roles/iam.serviceAccountUser`) on `write-number`'s runtime service account — to let Cloud Build deploy a revision that runs as that service account.

(If you set this trigger up via the Cloud Run resource's own **Connect to repo** button instead of a standalone Cloud Build trigger, these three roles are granted automatically — see the troubleshooting section for that alternative flow.)

## Security notes

- **Unauthenticated invocation is required** here because a browser (not a trusted backend) calls the function directly — but it also means anyone who discovers the function URL can call it repeatedly and inflate the counter. Consider **Cloud Armor** (rate limiting / IP allowlisting) in front of the function via a serverless NEG backend, or a simple shared-secret header check in `main.py`, if this needs to be more robust than a portfolio project.
- Prefer the **Secret Manager** reference for `DB_PASS` over a plain environment variable (Cloud SQL path).
- The `visitors_app` MySQL user only needs `UPDATE` and `SELECT` on the `visitors` table — avoid granting it broader access.
- The Firestore path's `roles/datastore.user` is already fairly narrow; avoid `roles/datastore.owner` unless you have a reason to need it.
- A publicly readable Cloud Storage bucket is fine for static site assets (HTML/CSS/JS) but never put credentials or sensitive data in it.
- **Per the challenge's own requirement 15:** never commit GCP credentials or service account key files to either GitHub repo.
- **Terraform-specific:** your state file (in the `cloud-resume-2026-tfstate` bucket) contains `db_password` in plain text on the Cloud SQL path, because Terraform needs to track it. Lock that bucket down as tightly as the database itself — no `allUsers` access, IAM restricted to whoever/whatever runs `terraform apply` — and never commit a `terraform.tfvars` file containing real secrets to git.

## Troubleshooting: Cloud Build error — "unable to evaluate symlinks in Dockerfile path"

```
Step #0 - "Build": unable to prepare context: unable to evaluate symlinks in Dockerfile path: lstat /workspace/Dockerfile: no such file or directory
```

**What's happening:** this comes from a Cloud Build trigger whose **Build Configuration** is set to "Dockerfile" directly (a raw `docker build`), rather than the `cloudbuild.yaml` pipeline from section 8 — some setups (including earlier versions of this guide) used that simpler trigger type, which requires a file literally named `Dockerfile` at the repo root and nothing else. If you're following section 8's pipeline, you won't hit this, since that trigger type points at `cloudbuild.yaml` instead. If you do have a Dockerfile-type trigger and this error fires, it's because the repo doesn't have that file yet.

**Fix: add a `Dockerfile` to the repo root**, matching the one in section 8, alongside `main.py` and `requirements.txt`.

Steps:
1. Add the `Dockerfile` at the repo root (same directory as `main.py` and `requirements.txt`).
2. (Optional) Test it locally before pushing:
   ```bash
   docker build -t write-number-test .
   docker run -p 8080:8080 \
     -e DB_USER=visitors_app -e DB_PASS=yourpassword \
     -e DB_NAME=visitors_db -e INSTANCE_CONNECTION_NAME=cloud-resume-2026:us-east4:free-trial-first-project \
     write-number-test
   ```
   The `/cloudsql/...` socket won't exist locally, so DB calls will fail unless you also run the [Cloud SQL Auth Proxy](https://cloud.google.com/sql/docs/mysql/sql-proxy) — the container starting and responding to a request at all is enough to confirm the Dockerfile itself is correct.
3. Commit and push.
4. Console → **Cloud Build → Triggers** → confirm **Dockerfile directory** is `/` and **Dockerfile name** is `Dockerfile`.
5. Console → **Cloud Build → History** → confirm the build reaches the end and a new revision shows up on `write-number`.

If you'd rather avoid maintaining a bare Dockerfile-type trigger at all, switch it to the **Cloud Build configuration file** type pointing at the `cloudbuild.yaml` from section 8 — that gets you the test-gated pipeline requirement 14 actually asks for, instead of just a build-and-deploy.

### Terraform equivalent

This specific error — a missing `Dockerfile` — happens the same way regardless of who creates the trigger; it's a repo-content problem, not a Terraform problem. Terraform only enters the picture if your `cloudbuild.yaml`'s deploy step targets a Cloud Run service Terraform also manages: make sure that service already has the `lifecycle { ignore_changes = [...] }` block from section 4, or a `terraform apply` run after this fix could revert the image CI just deployed.

## Troubleshooting: recreating a deleted Cloud Build trigger for an existing Cloud Run resource

If your backend's Cloud Build trigger gets deleted (accidentally or otherwise), builds stop firing on push, but the existing `write-number` resource itself is untouched — its current revision, environment variables/secrets, database connection, and IAM roles all stay exactly as they were. You just need a new trigger wired back to the same resource.

**Recommended: reconnect from the resource's own page (handles IAM for you)**
1. Console → **Cloud Run** → click into your `write-number` resource.
2. On its details page, click **Connect to repo** (may also appear as **Set up Continuous Deployment**).
3. Select the source: your `cloud_resume_backend` GitHub repo → branch `^main$` → **Build type: Dockerfile** (if the repo has one from the fix above) or **Cloud Build configuration file** (to use the full tests → build → deploy pipeline from section 8) → build context `/`.
4. **Save**. Google Cloud creates a new Cloud Build trigger and automatically grants the Cloud Build service account the roles it needs to deploy into this *specific existing resource*: **Cloud Build Service Account**, **Cloud Run Admin**, and **Service Account User** (plus Developer Connect roles if your GitHub connection uses the newer GitHub App-based integration). You don't need to grant these by hand.
5. Push a small commit to confirm: watch **Cloud Build → History**, then confirm a new revision lands on `write-number`.

**Manual fallback** (if "Connect to repo" isn't available, or you want full control): recreate the trigger under **Cloud Build → Triggers → Create trigger** pointing at `cloudbuild.yaml`, and grant the Cloud Build service account the three roles listed in section 8 by hand.

Either way, you're reconnecting a *new* trigger to the *same* resource — nothing about `write-number` itself needs to be recreated.

### Terraform equivalent

If the deleted trigger was managed by Terraform, don't use the console's "Connect to repo" wizard to recreate it — that creates a second, console-managed trigger Terraform doesn't know about. Instead:
1. Check whether it's still tracked in state: `terraform state list | grep cloudbuild_trigger`.
2. If it's gone from state too, just run `terraform apply` again — the trigger's resource block is still in your `.tf` files, so Terraform recreates it with the same configuration, IAM bindings included.
3. If it's still tracked in state but was deleted out-of-band in the console, `terraform plan` will show it as needing to be created again; `terraform apply` fixes it the same way.

This is the one scenario where Terraform is strictly less error-prone than the console: there's no "which button do I click" step to remember — just `terraform apply`.
